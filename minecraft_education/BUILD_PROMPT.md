# マイクラ設計図メーカー — 再構築プロンプト

このファイルは、**このプロジェクトをゼロから作り直す／引き継ぐためのプロンプト**です。
AIエージェント（Claude / Gemini など）にこの中身をそのまま渡せば、同じものが作れます。

このプロジェクトは実際に何度も作り直しながら完成しました。
**「やってみて初めて分かった失敗」がここに全部書いてあります。**
知らずに作ると同じ穴に落ちるので、`【失敗から得た鉄則】` は必ず守ってください。

---

## 【ここから】

あなたはMinecraft Education（Bedrock系）向けの
**「レゴの組立説明書のような設計図」を自動生成するツール**を作ります。

### 誰のためのものか

学校やクラブの小中学生と先生。パソコンが得意でない人が、**印刷した紙を見ながら**
マイクラの中で建物や仕掛けを組み立てられるようにするのが目的です。

### 作るもの

1. **設計図HTML** — 1ファイルで完結（外部ファイル・CDN・通信を一切使わない）。
   ネットが無い学校のPCでもダブルクリックで開ける。中身は次の順:
   - 自動検品の結果バナー
   - 完成イメージ（アイソメトリックの立体図）
   - 材料リスト（ブロック別の必要数）
   - つくるときのポイント（向きや順番の注意書き）
   - **レッドストーン回路のくわしい図**（回路がある設計にだけ自動で付く）
   - 段ごとの作り方（1段目から順に、上から見た格子図）
2. **`/setblock`・`/fill` コマンド集** — ゲーム内のチャットに貼れば建つ
3. **Code Builder（MakeCode Python）用の自動建築コード**
4. **AIに設計させるためのプロンプト** — 利用者がGeminiに貼ると、
   設計データ（JSON）だけを出してくれる
5. **単体で動くビューア（viewer.html）** — 上のJSONを貼ると設計図が表示される

### 全体の作り

- **設計データ（JSON）** … AIが作る。下記の `ops`（4命令）と
  `notes`（作り方の注意）・`layer_notes`（段ごとの注意）だけ
- **レンダラ** … 設計データ → 設計図HTML。**図の正しさはすべてこちらが保証する**
- 座標: `x`=西→東 / `z`=北→南（図では上が北）/ `y`=段（0が最下段）

### 設計データ（JSON）の仕様

AIに出させるのは次の形の **JSONだけ**です。この形をそのまま利用者向けプロンプトに書き、
レンダラはこの形だけを解釈します（**AIの書いたコードは実行しない**）。

```json
{
  "name": "作品の名前",
  "description": "どんな作品か2〜3文で。大きさや特徴、遊び方を書く",
  "ops": [
    { "op": "fill", "x1": 0, "y1": 0, "z1": 0, "x2": 8, "y2": 0, "z2": 6, "block": "cobblestone" },
    { "op": "box",  "x1": 0, "y1": 1, "z1": 0, "x2": 8, "y2": 3, "z2": 6, "block": "oak_planks" },
    { "op": "set",  "x": 4, "y": 1, "z": 6, "block": "door" },
    { "op": "clear","x": 4, "y": 2, "z": 6 }
  ],
  "notes": [
    "つくるときのポイントを1項目1文で。特に置き物の向きと順番"
  ],
  "layer_notes": {
    "2": "この段だけの注意書き。無くてもよい"
  }
}
```

**命令は4種類だけ**です。上から順に実行し、**後の命令が前を上書き**します。

| op | 意味 | 必要なキー |
|---|---|---|
| `fill` | (x1,y1,z1)〜(x2,y2,z2) の直方体を**中身までぎっしり**埋める | `x1..z2`, `block` |
| `box` | 同じ範囲の**外周の壁だけ**作る（床・天井は作らない＝中は空洞） | `x1..z2`, `block` |
| `set` | 1マスだけ置く | `x`,`y`,`z`, `block` |
| `clear` | 1マスを空にする（ドアの上や窓の穴あけに使う） | `x`,`y`,`z` |

- `block` は**パレットにあるキーのみ**。無いブロックは検品で弾く
- 座標の大小は逆でも受け付ける（内部で min/max に正規化する）
- `layer_notes` のキーは **`y` の値**（`"0"` が1段目、`"2"` が3段目）。
  `ops` の `y` とそろえる。**設計図の見出しだけが「◯段目」と1から数える**
  — ここは説明を間違えやすいので、プロンプトの文面も必ず突き合わせること

### 向きの指定（階段・トラップドア・はしご等）

向きの要るブロックには `facing` を付けさせます。付いていないと図と現物が食い違い、
コマンド出力も既定の向きになってしまいます。

```json
{ "op": "set", "x": 3, "y": 1, "z": 2, "block": "oak_stairs", "facing": "north" }
```

- 値は `north`（北＝図の上）/ `south`（南＝下）/ `east`（東＝右）/ `west`（西＝左）、
  ホッパー・オブザーバー等は `down` / `up` も取る
- 設計図のマスに**向きの矢印**を描く。作る人が迷わないための最重要表示
- 向きが要るブロック: 階段・トラップドア・フェンスゲート・はしご・チェスト・
  ピストン・ディスペンサー・ドロッパー・ホッパー・リピーター・コンパレーター・オブザーバー
- **そのブロックに指定できない向き**（階段の上下など）は検品で弾く

## 【失敗から得た鉄則】ここを守らないと必ず同じ失敗をします

### 品質の作り方

1. **AIに図を描かせない。** AIには設計データ（座標とブロック名）だけを作らせ、
   図・材料リスト・説明書はすべて決定的なコードで描く。
   こうしないとAIの出来不出来で図が崩れる。
2. **AIの出力コードを実行しない。** 学校で複数人が使う以上、
   任意コード実行は避ける。JSONの命令だけを解釈する。
3. **人が見落とす間違いは機械に検出させる。** 設計図を開いた瞬間に自動検品し、
   結果をページ上部に出す。利用者はその文面をそのままAIに見せれば直せる。

### 検品（validate）に必ず入れるルール

実際にこれらを見逃して、動かない設計図を作ってしまいました。

| 検出すべき問題 | なぜ必要か |
|---|---|
| **注記の座標が図の座標と食い違う** | 表示は0起点に正規化されるため、生座標で注記を書くとズレる。**最も多く、最も気づけない失敗** |
| **ピストンの前2マス目がふさがっている** | ピストンは前1マスのブロックを前2マス目へ押し出す。ふさがっていると永久に動かない |
| **ピストンの向きが未指定** | 向きが読めなければ作れない |
| **そのブロックに指定できない向き** | 階段やチェストは上下を向けない。指定しても無視され、図と現物が食い違う |
| 空中に浮いたブロック | 置き間違いに見える |
| パレットに無いブロック | 存在しないブロックは作れない |
| 大きすぎる／段が多すぎる | 図が読めなくなる |
| 置き物の置き方が注記に無い | 向きが分からず作れない |

**浮きブロックの判定は「斜めの接触」も含めること。** 面の接触だけで判定すると、
階段を1段ずつずらす勾配屋根（いちばん使いたい表現）が全部エラーになります。

### Minecraftの事実は必ず一次データで確認する

**推測で書くと必ず外れます。実際にブロックIDを6件間違えました。**

- 参照データ: [Mojang/bedrock-samples](https://github.com/Mojang/bedrock-samples) の
  `metadata/vanilladata_modules/mojang-blocks.json`（約1400ブロック）
  → リポジトリに同梱し、照合ツールと回帰テストで毎回突き合わせる
- Bedrockの名前は新旧が混在していて**規則性がない**:

  | 日本語 | 正しいID | 間違えやすい名前 |
  |---|---|---|
  | オークのトラップドア | `trapdoor` | ~~oak_trapdoor~~ |
  | オークのフェンスゲート | `fence_gate` | ~~oak_fence_gate~~ |
  | 丸石の階段 | `stone_stairs` | ~~cobblestone_stairs~~ |
  | コンパレーター | `unpowered_comparator` | ~~comparator~~ |
  | リピーター | `unpowered_repeater` | ~~repeater~~ |
  | 看板 | `standing_sign` | ~~oak_sign~~ |
  | オークのドア | `wooden_door` | ~~oak_door~~ |

  一方 `oak_stairs` `oak_slab` `oak_fence` `oak_leaves` は新しい名前が正しい。
- **向きは指定しないと反映されない。** ブロック名だけの
  `/setblock` は既定の向きで置かれ、階段もホッパーも全部あさっての方を向く。
- **【最重要】Minecraft Education のコマンドはブロック状態構文が使えない。**
  `/setblock ~ ~ ~ sticky_piston ["facing_direction"=5]` は Bedrock 1.19.70 以降の
  書き方で、**Education（1.21.133 実機で確認）は `構文エラー: "=" は無効です` にする**。
  Education のバージョン番号は Bedrock 本体の世代と一致しない。
  正解は旧世代の**データ値方式**: `/setblock ~ ~ ~ sticky_piston 5`。
  データ値と向きの対応は絶対に推測しない。公式のワールド変換データ
  （pmmp/BedrockBlockUpgradeSchema の id_meta_to_nbt と nbt_upgrade_schema）から取り、
  黄金コピー（reference/bedrock_legacy_aux.json）としてテストで固定する。
  要点: 階段=weirdo値そのまま(0=東1=西2=南3=北) / トラップドアも同じ並び /
  ホッパー・ディスペンサー等=facing_direction値そのまま(0=下1=上2=北3=南4=西5=東、
  ホッパーに上は無い) / フェンスゲート=0=南1=西2=北3=東 /
  チェスト・はしごは2〜5の横4方向のみ / 看板=0=南4=西8=北12=東
- **【さらに罠】「格納値の数え方」と「見た目の向き」はブロックごとに別物。**
  実機テストで「ピストンとリピーターが逆」と発覚した。数値の意味論は
  Nukkit（旧世代Bedrockサーバー実装）の設置・動作コードで1ブロックずつ照合する:
  **ピストンは押す向きの正反対を格納**（上下も逆）、
  **リピーター・コンパレーターは矢印の逆＝入力側を格納**。
  他（チェスト=正面、ホッパー=注ぎ口、ディスペンサー=発射面、オブザーバー=観察面）は
  格納値そのまま。必ず実機の向き確認（check_muki.txt）で答え合わせをする
- 参考: 新方式のブロック状態の書き方はブロックごとに違う（同じ「向き」で6通りある）。
  図の描画や検品のための知識としては引き続き必要:

  | 状態プロパティ | 値 | 使うブロック |
  |---|---|---|
  | `weirdo_direction` | 0=東 1=西 2=南 3=北 | 階段 |
  | `direction` | 同上 | トラップドア |
  | `facing_direction` | 0=下 1=上 2=北 3=南 4=西 5=東 | ホッパー・ピストン・ディスペンサー・ドロッパー・はしご |
  | `minecraft:cardinal_direction` | `"north"` 等の文字列 | チェスト・コンパレーター・リピーター・フェンスゲート・ドア |
  | `minecraft:facing_direction` | `"down"` 等の文字列 | オブザーバー |
  | `ground_sign_direction` | 0〜15（0=南、時計回り） | 看板 |

- **向きの違うブロックを1つの `/fill` にまとめない。** まとめると向きが失われる。

### レッドストーンの設計知識

- **ピストンは前2マス目が空いていないと伸びない。** 2マス幅の自動ドアで
  通路の両どなりにピストンを置くと、互いの可動域が重なって永久に動かない。
  正しくは1マス外側に置き、動かす板をあいだに入れる:
  `ピストン(東) / ガラス / 通り道 / 通り道 / ガラス / ピストン(西)`
- **動力が来ている場所にピストンを置くと即座に伸びる。**
  動かす板を先に置き、**ピストンは最後**に置く手順を注記に書く
- **レッドストーントーチは真下のブロックが動力を受けると消える。**
  これで信号を反転でき、「ふだん閉・踏むと開く」自動ドアが作れる
- **コンパレーターは容器の中身の量を信号の強さにする。** 中身1個なら信号は1で、
  1マスも進まない。**リピーターで15に戻す**必要がある
- **コンパレーターの真横にダストを置くと止まる**（横入力が背面入力以上だと出力0）
- 「中身が入ったら撃つ」装置は、コンパレーター＋リピーターでディスペンサーに
  信号を戻すだけでよい。**クロック回路は要らず、空になると自然に止まる**
- ホッパー・ディスペンサーが無いと「全自動◯◯装置」はそもそも設計できない。
  パレットに無いと、AIは羊毛で代用して回路を放棄する（実際にそうなった）

### 見た目をMinecraftに近づける方法

**単色の立方体を並べても積み木にしか見えません。** 次の3つで別物になります。

1. **テクスチャ** — 16×16の升目に明るさを変えた長方形を置いた模様を
   SVGの `<pattern>` にし、アイソメの傾きに合わせて `patternTransform` で変形して敷く。
   - パターンは**ブロックの種類×3面（上・左・右）だけ**定義する。
     1ブロックずつ描くと図形が何万個になりHTMLが破裂する
   - **箱の大きさに関わらず敷く。** マスいっぱいの箱にしか敷かないと、
     トラップドアも階段もハーフも単色の板きれになる（実際にそうなった）
   - **上面と側面で模様と色を変えられるようにする。**
     草ブロック＝上が緑・側面が土、原木＝上が年輪・側面が樹皮
2. **ブロックの形** — Minecraftのブロックは立方体ばかりではない。
   「立方体の一部（位置のずれ・幅・奥行き・高さを個別指定）」を描く汎用関数を作り、
   その組み合わせで形を表現する:

   | ブロック | 実物の形 |
   |---|---|
   | レッドストーンダスト | 床に貼りついた線。**つながる向きへ腕が伸びる** |
   | レッドストーントーチ | 細い棒＋先端の火 |
   | リピーター・コンパレーター | 薄い板＋小さな灯2つ |
   | ホッパー | 上が広く下が細い漏斗 |
   | 感圧板・トラップドア | 床の薄い板 |
   | ピストン・ディスペンサー | ふつうの立方体（小さく描くと別物になる） |
   | 階段 | 下半分の箱＋矢印側の背の高い箱 |
   | 花・ランタン・看板 | 細い棒＋頭 |

3. **配線のつながり** — ダストを板で描くだけでは
   **どこからどこへつながっているか読めない**（実際にそうなった）。
   Minecraftと同じく、つながる向きへ線を伸ばす:
   - となりが同じ高さのダストか回路部品 → まっすぐ
   - となりの1段上にダストがあり自分の真上が空いている → 登る
   - となりの1段下にダストがあり手前がふさがっていない → 下る
   - 立体図では「中心＋腕」、上から見た図では「中心の四角＋線」で描く。
     段差の先には「上」「下」の文字を添える（高さの変わる配線がいちばん間違えやすい）

### 大きさと性能

- HTMLが太る原因は**空きマスを1マスずつ描くこと**と、
  **中に埋もれて見えないブロックまで描くこと**。
  罫線を1本のパスにまとめ、6面すべてを不透明ブロックに囲まれたものは描かない
- 上限は**実測して決める**（憶測で決めない）。この実装では
  64×64マス・48段・20000ブロックまで（最適化後で6.4MB・ブラウザ表示8秒）
- 上限内でも大きいものは「参考」として知らせ、**合格のままにする**

### 2つの実装を持つ場合の鉄則

このプロジェクトはPython版（開発・コマンド出力用）とJavaScript版
（利用者に配るビューア用）の2つを持ちます。

- **同じ設計から1バイトも違わないHTMLが出ることを、毎回自動で検証する**
- **二重管理をしない。** パレットやテクスチャ定義は片方を正本にし、
  もう片方へ機械的に転記する。手で写すと必ずズレて、品質が静かに下がる
- 利用者に配るファイル（プロンプト・ビューア）は**生成物**にし、
  直接編集を禁止する

### 作業の進め方

1. **実際に描いて目で見る。** ヘッドレスブラウザでスクリーンショットを撮り、
   「屋根が谷に見える」「配線が追えない」といった問題を自分で見つける
2. **自分がGeminiになったつもりでプロンプトを試す。**
   プロンプトの指示だけで設計を書いてみると、書き漏れが必ず露呈する
3. **見つけた不具合は必ず回帰テストにする。** このプロジェクトでは
   実際に起きた不具合25件ぶんのテストがあり、それが品質を支えている
4. **確認できないことは確認できないと書く。** 推測を事実のように書かない

```
minecraft_education/
├── blueprint/          Python版
│   ├── palette.py      ブロック定義（正本）
│   ├── model.py        ボクセルモデル（fill/box/set/clear と向き）
│   ├── render.py       設計図HTMLの描画（テクスチャ・形・回路図）
│   ├── blockstate.py   向き → Bedrockのブロック状態
│   └── makecode.py     コマンド集と自動建築コードの出力
├── gemini/             利用者に配るもの
│   ├── renderer.js     JS版レンダラ（Python版と1バイト一致）
│   ├── templates/      プロンプトとビューアのひな型
│   ├── PROMPT.md       ← 生成物（Geminiに貼る）
│   ├── viewer.html     ← 生成物（単体で動くビューア）
│   ├── AGENT_PROMPT.md ← 生成物（エージェント建築コードをGeminiに書かせる）
│   ├── sync_palette.py palette.py → renderer.js の転記
│   ├── build_pack.py   renderer.js → PROMPT.md / viewer.html の生成
│   ├── compare.py      Python版とJS版の一致検証
│   ├── test_pack.py    回帰テスト25件
│   └── test_validate.js 検品ロジックの検証
├── reference/          Mojang公式のブロック定義（同梱）
├── tools/verify_block_ids.py  IDと状態プロパティの照合
├── designs/            設計（Python）
└── LEARNING.md         調べたことの記録
```

**変更したら必ず全部通す:**

```bash
python3 gemini/sync_palette.py      # パレットを転記
python3 gemini/build_pack.py        # 配布物を作り直す
python3 tools/verify_block_ids.py   # 公式データと照合
python3 gemini/compare.py           # Python版とJS版の一致
node gemini/test_validate.js        # 検品ロジック
python3 gemini/test_pack.py         # 回帰テスト
```

- **このリポジトリで続きをやらせたいとき**: 上に加えて次を伝える
